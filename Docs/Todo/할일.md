**실제 합계 : 설계 한 판 + 구현·시험·문서 한 판.** 눈금(반나절)보다 짧게 끝났다 —
설계 문서에서 자료형과 검사 목록을 먼저 못 박아 두어 구현 중에 정할 것이 거의 없었기 때문이다.
**분 단위 실측값은 안 잰다** — 공수 툴로 재지 않았으므로 어림값을 적지 않는다.

- 시험 : `go test ./...` 8패키지 (검사 자체 시험 12개 포함). `testdata/repo-ok` · `repo-bad` 로 돌린다.
- ④의 검사는 **셀 수 있는 것만** 본다. 판단이 섞이는 것은 넣지 않았다.
- 프로토타입 폴더는 ④의 검사에서 **뺐다.**

### 1판을 만들며 밟은 함정 둘

| 함정 | 어떻게 됐나 |
| --- | --- |
| Go 의 `flag` 은 **첫 인자에서 옵션 읽기를 멈춘다** | `stage check <id> pass --note "…"` 가 통째로 실패했다. 파싱 전에 옵션을 앞으로 모으게 고쳤다 |
| 훅이 준 **상대 경로**가 현재 폴더 기준으로 풀렸다 | 검사가 조용히 아무것도 안 막았다. 저장소 뿌리 기준으로 풀게 고쳤다. **조용히 안 도는 검사가 가장 위험하다** |

| ⑩ | **읽기 전용 미리보기 슬라이더** | 브라우저 안에서만 값을 흔들어 곡선이 어떻게 움직이나 본다. 파일은 안 건드린다 | 2~3시간 |
| ⑪ | N일 자동 플레이 시뮬 | 표만 봐서는 안 보이는 「고이는 자원 · 막히는 구간」을 찾는다 | 반나절 |

- **실제 수치가 생기기 전에는 안 만든다.** 세로 조각 단계에서 수치표를 쓸 때가 시작점이다.
  그 전에는 만들 데이터가 없어 상상으로 만들게 되고, 상상으로 만든 툴은 다 틀린다.
- ⑩은 **꼭 넣는다.** 스프레드시트를 버리며 잃는 것의 대부분을 이 하나가 메운다.
- 웹에서 **고치기까지** 만들면 공수가 세 배로 뛴다(2.5일 → 6~8일). 「보기만」으로 시작한다.
